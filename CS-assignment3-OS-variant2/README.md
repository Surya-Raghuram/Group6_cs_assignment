# Blind OS Command Injection Lab --- Time-Based & Out-of-Band

A small educational web application for demonstrating **Blind OS Command
Injection (CWE-78)** through two techniques:

1.  **Time-based blind injection** --- infer command execution from a
    measurable delay in the HTTP response.
2.  **Out-of-band (OOB) blind injection** --- infer command execution
    from a callback received by a separate listener.

The application also provides secured versions of both demonstrations.
The vulnerable and secured implementations use **separate API routes**,
making it possible to compare their behaviour using the same input.

> **Safety:** This project intentionally contains vulnerable endpoints
> for a controlled cybersecurity lab so run it only on your own machine,
> keep it bound to `127.0.0.1`

## 1. What the web application does

The project is a browser-based **network diagnostic application**. It
provides two ping-based demonstrations:

-   **Time-based blind command injection**
-   **Out-of-band blind command injection**

For each demonstration, the user can select either **Vulnerable** or
**Secured** mode and submit a target through the web interface.

The browser sends the target to an Express.js API endpoint. The backend
runs the ping utility and returns a response to the frontend.

In vulnerable mode, user input is incorporated into a shell command. In
secured mode, the application validates the target and invokes the ping
executable with a separate argument array rather than passing a
constructed command string through a shell.

The OOB demonstration additionally uses a small local HTTP listener. It
receives and logs callbacks generated by the OOB test payload.

This is a teaching application: its purpose is to make the difference
between unsafe shell command construction and safer process execution
visible and testable.

## 2. How blind command injection works

OS command injection occurs when an application passes untrusted user
input into an operating-system command in a way that allows the input to
change the command being executed.

In a **blind** command injection vulnerability, the injected command may
execute, but its output is not returned in the application's HTTP
response. Therefore, the tester needs another way to determine whether
execution occurred.

This project demonstrates two detection techniques.

### 2.1 Time-based blind injection

A command separator can be used to append a delay command to the
original ping command.

Example payload for a Linux/macOS lab:

``` text
127.0.0.1; sleep 5
```

The vulnerable server constructs a command equivalent to:

``` bash
ping -c 1 127.0.0.1; sleep 5
```

The shell interprets the semicolon as a command separator. The ping
runs, followed by `sleep 5`.

The browser does not receive the output of `sleep`. Instead, the tester
observes that the request takes approximately five seconds longer. The
delay is evidence that the appended command executed.

### 2.2 Out-of-band (OOB) blind injection

An OOB payload makes the server send a separate network request to a
listener controlled by the tester.

Example payload for this local Linux lab, assuming `curl` is installed:

``` text
127.0.0.1; curl http://127.0.0.1:4445/callback
```

The vulnerable shell command runs ping and then executes curl. The curl
request reaches the local listener on port `4445`.

The browser still does not display the injected command's output.
Instead, the callback appearing in the listener terminal is evidence of
execution.

**Time-based vs OOB:** time-based injection is detected through elapsed
time; OOB injection is detected through an external interaction such as
an HTTP callback.

## 6. API routes and implementation separation

The vulnerable and secured implementations are deliberately exposed
through different routes.

  Demonstration   Vulnerable route         Secured route
  --------------- ------------------------ --------------------------------
  Time-based      `POST /api/blind/time`   `POST /api/blind/time/secured`
  OOB             `POST /api/blind/oob`    `POST /api/blind/oob/secured`

The route registration in `server.js` follows this design:

``` javascript
// Vulnerable routes are enabled only in lab mode.
if (isLabMode) {
  app.post('/api/blind/time', handleBlindTimePing);
  app.post('/api/blind/oob', handleBlindOobPing);
}

// Secured routes are registered separately.
app.post('/api/blind/time/secured', handleBlindSecuredPing);
app.post('/api/blind/oob/secured', handleBlindSecuredPing);
```

The frontend mode selector chooses which route to call. Selecting
Vulnerable sends the request to the vulnerable route; selecting Secured
sends it to the secured route.

This is a separation of backend handlers, not merely a visual change in
the interface. The vulnerable and secured paths have different
implementations.

The vulnerable routes are gated by `LAB_MODE` and are enabled for local
demonstrations with `npm run lab`. The secured routes are registered
independently.

## 7. Vulnerable implementations

The vulnerable handlers are:

-   `handleBlindTimePing`
-   `handleBlindOobPing`

Both follow the same unsafe execution pattern:

1.  Read the target supplied in the HTTP request body.
2.  Insert the target into a command string.
3.  Execute the constructed string using `child_process.exec()`.
4.  Return a generic response without exposing the command output.

The core issue is the construction of a shell command using untrusted
input:

``` javascript
const constructedCommand = `ping -c ${PING_PACKET_COUNT} ${target}`;

exec(constructedCommand, options, callback);
```

`exec()` executes a command through a shell by default. Consequently,
shell syntax in the input---such as a semicolon on POSIX systems---can
be interpreted by the shell as part of the command rather than as
ordinary target data.

The application intentionally does not return the command's output in
these blind handlers. The time delay or OOB callback is used as the
signal that the injected command ran.

The vulnerable code exists only for the educational demonstration and
should never be used as a production implementation.

## 8. Secured implementations

The secured handler is:

-   `handleBlindSecuredPing`

It is used by both secured routes. The handler applies two main
protections.

### 8.1 Validate the target

The handler checks that the submitted target is a valid IP address or an
allowed hostname format before attempting to run ping.

Inputs containing shell syntax such as `;` are rejected rather than
accepted as a target.

Validation is based on an allow-list: the application accepts the
expected input format instead of trying to enumerate every dangerous
character.

### 8.2 Execute the program without a shell

The secured handler builds an argument array and calls `execFile()`:

``` javascript
const args = [PING_COUNT_FLAG, PING_PACKET_COUNT, target];

execFile(PING_BINARY, args, {
  shell: false,
  timeout: COMMAND_TIMEOUT_MS,
  maxBuffer: MAX_BUFFER_BYTES
}, callback);
```

The executable and its arguments are supplied separately. With
`shell: false`, the input is not parsed as shell command syntax. A value
containing a semicolon is not treated as a request to execute a second
command.

The secured handler therefore:

-   Validates the target before execution.
-   Avoids constructing a shell command string.
-   Uses a separate argument vector.
-   Disables shell interpretation.
-   Applies a process timeout and output-buffer limit.
-   Returns a generic blind-mode response rather than exposing command
    output.

**Why use both validation and `execFile()`?** Shell-free execution
prevents shell metacharacters from being interpreted as shell syntax.
Validation additionally restricts the target to the format the
application actually expects. It is important to validate input even
when using a safe process API, because argument parsing and option
handling by the invoked program are separate concerns.

## 9. Running the application

### Prerequisites

-   Node.js 18 or later
-   npm
-   A system with the `ping` utility available
-   `curl` installed if you want to run the example OOB payload

Check the installed versions:

``` bash
node -v
npm -v
```

Install dependencies from the project directory:

``` bash
npm install
```

### Start the application in lab mode

``` bash
npm run lab
```

Open the application in your browser:

``` text
http://127.0.0.1:3000
```

Lab mode enables the intentionally vulnerable routes for the
demonstration. Keep the application local and stop it when testing is
complete.

### Start the OOB listener

Open a second terminal in the project directory:

``` bash
npm run listener
```

The listener runs separately from the Express application and waits for
callbacks on:

``` text
http://127.0.0.1:4445
```

Keep this terminal visible during the OOB demonstration so the callback
can be observed.

### Run the tests

If the repository includes the Node.js test suite:

``` bash
npm test
```

## 10. Demonstration and testing

Perform these tests only against the local lab application.

### Test A --- Normal ping

1.  Open the web application.
2.  Select either mode.
3.  Enter `127.0.0.1`.
4.  Click the corresponding Ping button.

The application should perform the normal ping diagnostic.

### Test B --- Vulnerable time-based injection

1.  Select Vulnerable in the time-based section.
2.  Submit:

``` text
127.0.0.1; sleep 5
```

3.  Observe the request duration.

The request should take approximately five seconds longer than a normal
request, subject to system and network timing. The browser does not
display the output of the injected command.

### Test C --- Vulnerable OOB injection

1.  Start the OOB listener in a second terminal.
2.  Select Vulnerable in the OOB section.
3.  Submit:

``` text
127.0.0.1; curl http://127.0.0.1:4445/callback
```

4.  Observe the listener terminal.

A callback should appear in the listener logs. This is the OOB evidence
of command execution.

### Test D --- Secured time-based injection

1.  Select Secured in the time-based section.
2.  Submit the same time-based payload:

``` text
127.0.0.1; sleep 5
```

The secured handler should reject the input during validation. The
injected sleep command should not run, so the deliberate five-second
delay should not occur.

### Test E --- Secured OOB injection

1.  Select Secured in the OOB section.
2.  Submit the same OOB payload:

``` text
127.0.0.1; curl http://127.0.0.1:4445/callback
```

The secured handler should reject the input. No new callback should
appear in the listener.

### Expected comparison

  -----------------------------------------------------------------------
  Behaviour               Vulnerable              Secured implementation
                          implementation          
  ----------------------- ----------------------- -----------------------
  Input handling          Inserts input into a    Validates input and
                          shell command string    passes it as a separate
                                                  argument

  Process API             `exec()`                `execFile()`

  Shell interpretation    Shell is invoked by     `shell: false`
                          default                 

  Time payload            Causes an observable    Rejected by validation
                          delay                   

  OOB payload             Triggers a listener     Rejected; no callback
                          callback                

  Command output          Not returned to browser Not returned to browser

A normal ping should still work in the secured mode. A rejected
malicious input is an expected security result, even though it does not
produce a successful ping.

## 11. Security considerations

-   **Localhost only:** The application and OOB listener are intended to
    bind to `127.0.0.1`, not a public or LAN-facing interface.
-   **Vulnerable mode is for demonstrations:** Start it only when
    required for the lab, and do not deploy it.
-   **Production safeguard:** The server includes a safeguard against
    enabling lab mode in a production environment.
-   **Input validation:** The secured handler allows only expected
    IP/hostname input.
-   **Shell-free execution:** The secured handler uses `execFile()` with
    `shell: false`.
-   **Execution limits:** The process execution options include a
    timeout and a bounded output buffer.
-   **No output disclosure in blind mode:** The blind handlers return a
    generic response rather than returning the executed command's
    output.
-   **Least privilege:** In a real deployment, the application should
    run as a dedicated low-privilege operating-system user.

The vulnerable examples are intentionally unsafe. The secured
implementation demonstrates safer command execution, but it does not
replace broader application security review, operating-system hardening,
or least-privilege deployment.

## 12. Key takeaways

1.  Blind OS command injection can be present even when command output
    is not returned to the browser.
2.  A measurable delay can reveal time-based command execution.
3.  An HTTP or DNS callback can reveal out-of-band command execution.
4.  Directly concatenating untrusted input into a command passed to
    `exec()` creates a shell-injection risk.
5.  Input allow-list validation and `execFile()` with `shell: false`
    provide a safer implementation for this ping use case.
6.  Keeping vulnerable and secured functionality on separate routes
    makes the difference explicit and supports a repeatable security
    demonstration.

**Core lesson:** Treat user input as data, never as part of an
operating-system command. Prefer APIs that execute a specific program
with separately supplied arguments, and validate input against the exact
format the application expects.
